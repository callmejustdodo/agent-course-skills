# 인터뷰·조사·결정 지침

## 질문 순서

한 번에 핵심 질문 하나만 묻고 답변을 기록한다. 질문 목록을 사용자에게 한꺼번에 던지지 않는다.

1. 담당 범위와 반복되는 업무들을 큰 단위로 나열한다.
2. 사용자가 범위와 우선순위를 고친다.
3. 우선 업무의 실제 사례를 시작부터 끝까지 따라간다.
4. 단계별 조건·도구·사람 판단·예외를 보충한다.
5. 흐름을 되짚어 누락과 순서를 확인한다.
6. 각 단계의 처리 방식과 조사할 기능 요구를 정한다.
7. 공식 자료를 조사해 현재 방법과 대안을 비교한다.
8. 실행·데이터·채널·시작 방식을 따로 논의한다.
9. 다음 업무로 이동하거나 사용자가 나머지를 명시적으로 보류한다.
10. 기존 스킬로 처리되지 않는 반복 절차의 생성 범위를 합의하고 실제 스킬로 만든다.

이미 자료에 있는 답을 다시 묻지 않는다. 답변에 따라 다음 질문을 고른다. 질문 예시는 다음과 같다.

- “그 일을 시작하게 만든 실제 사건은 무엇이었나요?”
- “그 단계에서 무엇을 보고 어떤 판단을 하나요?”
- “결과를 누구에게 어떤 형태로 넘기나요?”
- “정보가 없거나 로그인이 풀리면 지금은 어떻게 처리하나요?”
- “내 컴퓨터가 꺼져 있어도 이 단계가 실행돼야 하나요?”
- “이 자료가 외부 모델이나 서버로 이동해도 되나요?”

## 조사 시작 조건

제품 이름부터 찾지 말고, 최소한 다음을 식별한 뒤 필요한 기능을 검색한다.

- 단계의 입력·출력과 필요한 실제 행동
- 현재 사용 중인 서비스·앱 또는 작업 환경

권한·API 지원·비용·데이터 위치가 미확인이면 조사를 미루지 않는다. 해당 항목을 조사할 제약이나 다음 질문으로 기록하고, 공식 문서로 확인 가능한 부분부터 찾는다.

검색어는 “고객사 이름 + 내부 업무”가 아니라 “공유 메일함에서 초안 저장 API”, “macOS 데스크톱 앱 자동화 공식 문서”처럼 일반화한다.

## 출처와 비교

우선순위는 공식 문서·공식 저장소·공식 스킬 카탈로그, 그다음 신뢰할 수 있는 기술 문서다. 가격·기능·플랫폼 지원처럼 바뀔 수 있는 정보는 조사 당일 다시 확인한다.

각 신규 추천에는 최소 한 개의 정확한 출처를 붙인다. 홈페이지가 아니라 해당 기능·설치·제약을 직접 설명하는 페이지를 선호한다. 스킬은 실제 패키지나 `SKILL.md`의 위치를 확인한다.

웹이나 문서 검색 도구를 사용할 수 없으면 출처를 만들어내지 않는다. 조사 상태를 `미확인`으로 남기고, 사용 가능한 대화 정보만으로 임시 비교안을 작성한다.

비교 단위:

- 현재 방식: 그대로 쓸 수 있는지, 부족한 기능은 무엇인지
- 대안: 필요한 행동 지원, 인증·최소 권한, 운영체제·런타임 호환
- 안정성: 오류 확인, 재시도·중복 방지, 결과 검증
- 운영 부담: 비용, 설정·유지, 담당자, 벤더 종속
- 데이터: 전송·저장 위치, 접근 범위, 회사 정책

추천 상태는 `조사 확인`, `설치 확인`, `인증 확인`, `기능 실행 확인`, `업무 결과 확인`으로 나눈다. 문서만 읽었다면 첫 번째만 확인이다.

## 결정 방식

AI는 다음 형태로 기본안을 제시한다.

> W01-S03은 현재 Google Drive 연결을 재사용해 조회하고, 초안 저장까지만 허용하는 구성이 가장 작습니다. PC 종료 후 실행 요구가 없으므로 로컬 런타임으로 시작합니다. 팀 채널과 서버는 사용자가 늘거나 예약 실행이 필요할 때 검토합니다.

그 뒤 결정을 바꿀 핵심 조건 하나를 묻는다. 사용자가 선택하면 `사용자 합의`, 아직 답하지 않았으면 `추천`, 사용자가 나중으로 미루면 `명시적 보류`, 권한·제품 지원이 막히면 `보류`, 근거가 없으면 `미확인`으로 기록한다. 중요한 선택은 `사용자 합의`나 `명시적 보류` 없이 결정된 것으로 닫지 않는다.

수동·규칙 기반 처리가 더 적합한 단계도 동등한 결론이다. 새 도구를 고르는 것이 완료 조건이 아니다.
